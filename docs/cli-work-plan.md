# План работ: доведение CLI до рабочего состояния + роадмап

Дата: 2026-06-25
База работ: ветка `docs/readme-and-demo-brief` (текущая линия, ~41 коммит готовых блоков:
`JMeterPlanSerializer`, пакет `plan/`, `@lint`/`@wrap`, режимы контекста чата).
Референс: прототип `origin/claude/add-cli-integration-l3ixk` (CLI-сервисы + интеграция в чат,
но stale: 4 впереди / 41 позади текущей линии). Решение: **портировать сервисы на текущую линию**,
не мёржить и не развивать саму ветку.

OpenAI и DeepSeek сознательно убраны — не нужны. Целевые провайдеры: Qwen Code CLI (приоритет),
GigaCode CLI (по мере подтверждения возможностей), GigaChat (остаётся как облачный фолбэк).

Горизонт: Этапы 0–5 (вплоть до встроенного MCP). Параллельно — роадмап-фичи.

## Этап 0 — спайк-валидация (2–3 дня, ДО кода apply-движка)

Цель: go/no-go по протоколу fenced-ops для каждого провайдера, прежде чем строить движок правок.

- Руками собрать пример контекста: выход `JMeterPlanSerializer.toReadableTree()` + system-prompt протокола.
- Прогнать 20–30 реальных задач редактирования против живых установок qwen и gigacode на Windows.
- Измерить: первичный schema-комплаенс, recovery-after-error, реальное наличие флагов GigaCode
  (`-p`, `--output-format json`, `--resume`).
- Зафиксировать минимальную версию qwen-code для пина (`--output-format` отсутствовал в ранних — issues #795, #873).

Выход: решение go/no-go по варианту B на провайдера. Если комплаенс плохой — разворот к MCP-инструментам (Этап 5) раньше.

## Этап 1 — рабочий subprocess-слой + порт в чат (~3–4 дня) — ПРИОРИТЕТ

Цель: CLI реально работает как чат-провайдер на Windows. Закрывает все блокеры прототипа.

Новый `service/cli/CliTransport` (вместо прямого `ProcessBuilder` в `CliAiService`):

- **Windows-резолв команды**: `cmd /c` либо резолв полного пути `.cmd`-шима (PATHEXT), учёт JDK-8221858
  (кавычки в аргументах). — *закрывает блокер №1: 100%-фейл запуска `qwen.cmd`*.
- **`waitFor(timeout)` управляет жизнью процесса**, чтение stdout/stderr — в отдельных потоках.
  — *закрывает блокер №2: мёртвый таймаут на `readAllBytes()` до `waitFor`*.
- **Конкурентный дренаж stdout и stderr** отдельными нитями. — *закрывает блокер №3: двухканальный дедлок*.
- **Промпт через stdin или временный файл, не через argv** — снимает лимит ~32 767 символов Windows;
  путь temp-файла без пробелов/корректно экранирован.
- **Явная кодировка** вывода (не безусловный UTF-8) — фикс mojibake при cp1251.
- **Честная отмена**: `destroy()` + `toHandle().descendants()`, проброшенная в UI; shutdown-hook.

Парсинг ответа:

- Настоящий JSON-парсер (Jackson — проверить, что он в зависимостях текущей линии) вместо `CONTENT_PATTERN`.
  — *фикс «ломает все русские ответы»: разэкранирование `\uXXXX`, верный порядок unescape, защита от чужого
  поля `content` в tool-call событиях*.

Порт сервисов:

- `QwenCodeCliService` / `GigaCodeCliService` поверх **capability-record** (`supportsResume`,
  `systemPromptFlag`, `jsonOutput`) вместо наследования по префиксу свойств; свойство
  `<prefix>.cli.transport=auto|resume|oneshot` с одноразовой пробой `--help`.
- `--yolo` по умолчанию выключен; file-write инструменты CLI отключить через `excludeTools`.
- Регистрация провайдеров в дропдауне `AiChatPanel` текущей линии (конфликтная зона — аккуратно с
  маршрутизацией `openai:`/`giga:` → заменить на `qwen-cli:`/`gigacode-cli:`/`giga:`).
- Документировать `qwen.cli.*` / `gigacode.cli.*` в `jmeter-ai-sample.properties`.
- Юнит-тесты на `CliTransport` (таймаут, ненулевой exit, дренаж stderr, отмена) и парсер ответа (кириллица).

Критерий готовности: на чистом Windows установить qwen, выбрать в дропдауне, получить корректный
русский ответ; зависший процесс отменяется кнопкой; большой stderr не вешает панель.

## Этап 2 — подмешивание контекста JMeter (~3–4 дня)

- Врезать `JMeterPlanSerializer` (node-ID + revision-hash) в промпт CLI-провайдеров; режимы контекста чата уже есть.
- `@this` → информация об элементе уходит агенту и пишется в историю (фикс display-only).
- Фикс чередования ролей: структурированная история `role+text` вместо чётных/нечётных индексов
  (ломалось после любой @-команды — затрагивает и GigaChat).
- `updateCurrentNode()` перед каждым экспортом контекста; чтение дерева — снапшотом с EDT (`invokeAndWait`),
  не из `doInBackground`.
- Редакция чувствительных данных (хосты, креды) в сериализованном плане перед отправкой в облачный CLI.

## Этап 3 — мутации тест-плана через fenced-ops (~1–1.5 недели)

- Протокол: `--append-system-prompt` инструктирует агента отвечать блоком ` ```jmeter-ops ` с JSON-операциями
  `set_property / add_element / remove_element / replace_subtree / new_test_plan / get_element`.
- `service/ops/`: схема операций + парсер + валидатор; извлечение последнего полного fenced-блока.
- Применение через существующий `plan/`-конвейер: превью (`PlanPreviewRenderer`) → подтверждение →
  применение на EDT → JMX-снапшот для отката (`PlanApplyUndoStore` → кольцевой буфер) + чип «Откатить изменение агента».
- nodeId-реестр со структурной ошибкой «stale id, re-fetch tree» (самокоррекция агента) + revision-hash.
- Dirty-flag конфликт-гард: правки дерева во время хода агента → блок авто-применения, выбор «моё/агента/отмена».
- Генерация целого теста: `new_test_plan` → JMX-фрагмент через `SaveService` → загрузка с превью.
- Отключить regex-перехват `JMeterElementRequestHandler` для CLI-провайдеров (AI-driven editing вместо сентинелов).
- Плагинная валидация плана после каждого батча операций.

Самое рискованное допущение (проверено на Этапе 0): модели стабильно выдают схемно-валидный fenced-JSON
с корректными node-ID. Если плохо — разворот к Этапу 5 (схему форсирует протокол MCP).

## Этап 4 — сессии, стриминг, UX (~1 неделя)

- **Стриминг + Stop** (роадмап): `--output-format stream-json --include-partial-messages` →
  инкрементальный рендер в чат + кнопка отмены вместо ~60 c заблокированного ввода.
- **Сессии** `--resume <sessionId>` для qwen (id из JSON-конверта первого ответа); переотправка контекста
  только при смене revision-hash дерева — temp-файл истории больше не нужен. GigaCode: фолбэк на файл-историю.
- Threading/гонки: блокировка кнопки «новый чат» во время запроса; удаление индикатора «думает» на @code-пути;
  жизненный цикл при закрытии панели (cancel + kill process tree).
- Итерации промпт-инжиниринга протокола против реальных моделей (длинный хвост).

## Этап 5 — встроенный MCP-сервер (фаза 2)

- HTTP MCP в JVM JMeter (127.0.0.1, случайный порт, bearer-токен) с инструментами
  get/update/add/remove element + validate; генерируемый per-session `settings.json`.
- Требует решения по Java 17 в pom (JMeter 5.6.3 работает на 17) **или** hand-rolled JSON-RPC (~700–900 LOC).
- Добавляется поверх fenced-ops без выброса кода; схему здесь форсирует протокол (надёжнее регулярных промптов).

> Замечание по pom: прототип использует `Files.writeString` (Java 11) и `InputStream.readAllBytes` (Java 9)
> при `source/target` 8/9 — при порте зафиксировать целевую версию Java явно.

## Параллельный трек — роадмап-фичи (не блокируются CLI)

### `@plan import <url>` (после Этапа 2)
- Загрузка HTML по URL → извлечение текста сценария по тегам/селекторам → преобразование в draft test plan
  с превью перед apply.
- Безопасность: доменный allowlist, таймаут/лимиты размера, санитизация контента, anti-injection
  (явный запрет следовать инструкциям из загруженного контента).

### Тех-долг промптов/кода (можно вести с Этапа 1)
- `High` — `@lint`: строгий JSON-контракт ответа + валидация вместо парсинга `Element X: NEW_NAME`
  (`lint/ElementRenamer.java`).
- `Medium` — `@plan`: усилить anti-injection и валидацию (запрет инструкций из `Scenario`, строгая схема,
  проверка лишних полей) (`plan/PlanCommandHandler.java`).
- `Medium` — `@optimize`/`@this`: стабильный формат ответа (структура, лимит длины, actionable-блоки)
  + лимиты/фильтрация свойств в промпте (`optimizer/OptimizeRequestHandler.java`, `gui/AiChatPanel.java`).
- `Low` — унификация языка промтов (рус/англ) для предсказуемого стиля.
- `Low` — фикс mojibake в UI-строках (`gui/MessageProcessor.java` и смежные).

> Примечание: пункты тех-долга про `OpenAiService` из старого TODO неактуальны — OpenAI удалён.

## Последовательность и зависимости

1. **Этап 0** (спайк) — обязательно первым, до движка правок.
2. **Этап 1** (рабочий чат) — основной приоритет; разблокирует всё остальное и сам по себе даёт ценность.
3. **Этап 2** (контекст) — нужен и для качества чата, и как фундамент для fenced-ops; здесь же стартует `@plan import`.
4. **Этап 3** (правки) — зависит от 0 (go) и 2.
5. **Этап 4** (стриминг/сессии/UX) — поверх 1–3.
6. **Этап 5** (MCP) — фаза 2, опционально/при плохом комплаенсе моделей.

Тех-долг промптов/кода — фоном, начиная с Этапа 1.

## Статус реализации (обновлено 2026-06-25)

**Этап 0 (live go/no-go) — GO.** Прогон реального пайплайна (OpsProtocol → qwen → extract → parse →
validate) на машине с qwen-code 0.18.1. Локальная модель `qwen3.6:35b` — рабочая, но медленная и
нестабильная (263с … таймаут 600с; +~60с на `managed-auto-memory-extractor`). Облачная
`qwen3-coder-next` — ~30с, стабильно. Модель выдаёт корректный fenced-блок `jmeter-ops`.
Найден и исправлен реальный баг совместимости: модель отдаёт `props` массивом, парсер теперь
принимает объект/массив (юнит-тест на точном выводе qwen). Замечание: модель иногда кладёт заголовок
в `set_property HTTPSampler.headers` вместо Header Manager — структурно валидно, но семантически
неверно для JMeter → задача промпт-инжиниринга (Этап 4, длинный хвост). Латентность подтверждает
приоритет стриминга+Stop (Этап 4).


**Этап 1 — ГОТОВО.** `service/cli/` (CliTransport, CliResponseParser, CliCapabilities, ArgsParser,
CliAiService) + провайдеры Qwen/GigaCode, регистрация в дропдауне и маршрутизация, документация в
`jmeter-ai-sample.properties`. Легаси `CliService` удалён; `service.type=cli|qwen|gigacode` теперь
ведёт на новый транспорт (`AiMenuItem`), дефолт-провайдер в дропдауне знает про qwen/gigacode.
17 юнит-тестов транспорта/парсера зелёные.

**Этап 2 — ГОТОВО (по части CLI).** `JMeterPlanSerializer.toReadableTree()` теперь печатает `#id`
на каждый элемент + добавлен `SerializedPlan.revisionHash()`. CLI-запрос несёт протокол jmeter-ops
и дерево с id и revision (`withCliOpsContext`). Отложено (вне рамок CLI, помечено): переход на
структурную историю role+text (плагин-wide; текущий i%2 на CLI-пути корректен — баг был только в
удалённом прототипе), запись `@this` в историю, редакция чувствительных данных.

**Этап 3 — ГОТОВО (движок + интеграция); ждёт ручной валидации.** Пакет `service/ops/`:
`OpType`, `PlanOp`, `FencedOpsExtractor` (последний полный блок), `PlanOpsParser` (строгий,
whitelist полей), `PlanOpsValidator` (проблемы списком), `OpsPreviewRenderer`, `ElementTypeAlias`,
`OpsProtocol` (system-prompt), `OpsApplier` (EDT, revision-guard, разрешение id через свежую
сериализацию), `OpsUndoStore` (пакетный откат инверс-действиями), `OpsApplyResult`.
Интеграция в `AiChatPanel`: инъекция протокола+контекста, отключение regex-перехвата для CLI,
превью→подтверждение→применение, откат через `@rollback`. 34 юнит-теста протокола зелёные,
весь набор — 100 зелёных. `new_test_plan` через CLI намеренно отклоняется (деструктивно, вне undo —
направляет на `@plan`). **Не закрыто:** Этап 0 — прогон против живых qwen/gigacode (движок правок
протестирован только на уровне протокола, не end-to-end), полноценный JMX-snapshot undo,
replace_subtree пока best-effort (remove+add по type).

**Этап 4 (сессии, стриминг, UX) — ГОТОВО.** (a) Кнопка **Стоп** прерывает запрос: `SwingWorker.cancel`
+ `CliAiService.cancel()` (kill process tree), блокировка «новый чат» во время запроса, `shutdown()`
при закрытии панели. (b) **Стриминг**: `--output-format stream-json --include-partial-messages`,
построчный дренаж в `CliTransport`, `StreamJsonParser` (TDD, 7 тестов), инкрементальный рендер в чат;
дельты собираются, финал берётся из события `result`. (c) **Сессии** (`*.cli.sessions`, по умолчанию
off): `--chat-recording` + `--resume <session_id>`, захват id из ответа; при активной сессии шлётся
только новый ход, дерево — лишь при смене revision; сессия сбрасывается на «новый чат». Механизм
`--resume` проверен вживую (2 хода, модель вспомнила кодовое слово). Этап 5 (встроенный MCP) —
не делаем: комплаенс моделей GO, fenced-ops достаточно.
