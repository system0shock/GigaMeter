# Интерактивная CLI-интеграция: дизайн и план портирования

Дата: 2026-06-10
Статус: черновик, ожидает продолжения работы (решение по базе принято, дизайн не утверждён окончательно)

## 1. Контекст и цель

Ветка `claude/add-cli-integration-l3ixk` добавила CLI-провайдеров (Qwen Code CLI, GigaCode CLI),
но в режиме «просто чат»: one-shot subprocess на каждое сообщение, история через временный файл,
ноль контекста JMeter, нет канала «агент → изменение тест-плана».

**Цель:** интерактивная интеграция CLI-агентов:
1. живое подмешивание контекста JMeter (дерево тест-плана, выбранный элемент);
2. изменение тест-плана на лету: правка отдельных элементов, добавление/удаление, генерация теста целиком;
3. provider-agnostic: qwen сегодня, GigaCode по мере подтверждения возможностей.

## 2. Принятое решение: база работ

**Портируем CLI-сервисы на локальную линию `docs/readme-and-demo-brief`** (а не развиваем CLI-ветку).

Обоснование: локальная линия содержит ~40 коммитов с уже готовыми строительными блоками,
которых нет на CLI-ветке:
- `utils/JMeterPlanSerializer` — компактная сериализация дерева (JSON + `toReadableTree()`, node-ID, лимиты);
- пакет `plan/` — `@plan analyze/apply`: `PlanCommandHandler`, `PlanDraftGenerator`, `PlanDraftValidator`,
  `PlanPreviewRenderer`, `PlanApplyUndoStore` (превью + применение + откат);
- `@rollback`, переключаемые режимы контекста чата, подмешивание выбранного JSR223-скрипта.

CLI-сервисы — новые файлы, портируются легко; конфликтная зона — `AiChatPanel` (диспетчеризация провайдеров).

### Блокеры (high) — субпроцессный слой `CliAiService`
| # | Находка |
|---|---------|
| 1 | **Windows: `ProcessBuilder("qwen")` не запускает npm-shim `qwen.cmd`** (CreateProcess не применяет PATHEXT) — воспроизведено на JDK 21, `IOException error=2`. Документированный happy-path падает в 100% случаев. Нужен `cmd /c` либо резолв полного пути `.cmd` (+ учёт JDK-8221858 про аргументы с кавычками). |
| 2 | **Таймаут — мёртвый код**: `readAllBytes()` на stdout вызывается до `waitFor(timeout)`; зависший CLI (OAuth-логин qwen и т.п.) блокирует SwingWorker навсегда, панель заблокирована до перезапуска JMeter. |
| 3 | **Двухканальный дедлок**: stdout читается полностью до stderr при `redirectErrorStream(false)`; >4КБ stderr (телеметрия/tool-trace qwen) → child блокируется на записи stderr, parent — на чтении stdout. |

### Серьёзные (major)
- Промпт одним аргументом `-p` → лимит 32 767 символов командной строки Windows (большой тест-план не влезет). Транспорт контекста — через файл или stdin.
- Regex-парсинг JSON (`CONTENT_PATTERN`): не разэкранирует `\uXXXX` → **ломает все русские ответы**; неверный порядок unescape; может зацепить чужое поле `content` при tool-call событиях. Нужен настоящий JSON-парсер.
- `@this` — display-only: информация об элементе не уходит в AI и не пишется в историю.
- Чередование ролей в `conversationHistory` ломается после любой @-команды → роли user/assistant перемешаны во всех последующих промптах (затрагивает и GigaChat, и CLI).
- Чтение/мутация GUI-дерева из `doInBackground` (не EDT-safe): `getCurrentElementInfo`, optimizer, lint/wrap-мутации.
- Гонка: кнопка «новый чат» активна во время запроса и чистит `conversationHistory`, который копирует worker.
- 60+ секунд заблокированного ввода, без прогресса/стриминга/отмены.
- Маршрутизация element-request по английской строке-сентинелу `"I couldn't understand what to do with"`.

### Прочее (medium/minor, выборочно)
- История диалога копится в `%TEMP%` (deleteOnExit не срабатывает в долгих GUI-сессиях), путь с пробелами ломает `@file`-ссылку.
- `--yolo` = авто-одобрение файловых/shell-действий, управляемых выводом модели.
- stdout/stderr безусловно декодируются как UTF-8 (можибейк при cp1251).
- `extra_args.split("\s+")` ломает аргументы в кавычках.
- Сырой stderr уходит в чат; промпт виден в списке процессов ОС.
- Дубли: `getCurrentElementInfo` повторён в двух классах; GigaChat- и CLI-пути дублируют механику истории.
- Abstract-class-per-CLI: подклассы отличаются только префиксом свойств, база зашивает qwen-специфику.

## 4. Архитектура: Fenced-Ops протокол (вариант B, рекомендация судьи 40/50)

Сравнивались три варианта (полные проработки — в JSON-отчёте):
- **A. Встроенный MCP-сервер** в JVM JMeter (34/50) — высокий потолок, но pom зажат на Java 8
  (MCP Java SDK требует 17) и опора на `--input-format stream-json`, который официально «under construction». → **Фаза 2.**
- **B. Fenced-Ops протокол** (40/50) — **выбран**. Единственный, целиком построенный на возможностях,
  подтверждённых официальной документацией qwen.
- **C. Персистентная ACP-сессия** + filesystem-as-API (31/50) — ACP экспериментален, флаг дрейфовал
  (`--experimental-acp` → `--acp`), деприоритизирован мейнтейнерами. → **Фаза 3.**

### Суть варианта B
1. **Контекст →** плагин сериализует дерево (через существующий `JMeterPlanSerializer`, с node-ID и
   revision-hash) + полный JMX выбранного элемента в контекст; передача через файл/stdin, не через argv.
2. **Протокол →** `--append-system-prompt` инструктирует агента отвечать fenced-блоком
   ` ```jmeter-ops ` с JSON-операциями: `set_property / add_element / remove_element / replace_subtree /
   new_test_plan / get_element`.
3. **Применение →** плагин валидирует ops → превью с per-op диффом → подтверждение → применение к живому
   дереву на EDT через существующий `plan/`-конвейер → JMX-снапшот для отката. Никакого `--yolo`;
   file-write инструменты CLI отключаются через settings `excludeTools`.
4. **Сессии →** qwen: `--resume <session_id>` (id из JSON-конверта первого ответа) — временный файл истории
   не нужен; контекст переотправляется только при смене revision-hash дерева. GigaCode: fallback на
   историю-файл, пока возможности не подтверждены.
5. **Стриминг →** `--output-format stream-json --include-partial-messages` → живой вывод в чат + кнопка Stop.

### Обязательные грэфты из A и C
- `AgentSession`-интерфейс + per-provider capability record (`supportsResume/systemPromptFlag/jsonOutput`),
  свойство `<prefix>.cli.transport=auto|resume|oneshot` с одноразовой пробой `--help`.
- nodeId-реестр со структурной ошибкой «stale id, re-fetch tree» (агент самокорректируется).
- Windows-гигиена процессов: `cmd /c` для `.cmd`-шимов, раздельный дренаж stderr отдельным потоком,
  `waitFor(timeout)` до чтения, убийство дерева процессов `toHandle().descendants()`, shutdown-hook.
- `updateCurrentNode()` перед каждым экспортом контекста (несохранённые правки GUI попадают агенту).
- Кольцевой буфер JMX-снапшотов + чип «Откатить изменение агента» в чате (расширение `PlanApplyUndoStore`).
- Dirty-flag конфликт-гард: пользователь правил дерево во время хода агента → блок авто-применения,
  выбор «моё/агента/отмена».
- Плагинная валидация плана после каждого батча операций.

### Самое рискованное допущение (валидировать ПЕРВЫМ)
Что модели (прежде всего GigaCode) стабильно выдают схемно-валидный fenced-JSON с корректными node-ID
и реальными ключами свойств JMeter, и самокорректируются от структурных ошибок. GigaCode CLI публично
не документирован; предположение «флаги как у qwen» не подтверждено ничем, кроме косвенного признака
(gigadoc-mcp использует `~/.gigacode/settings.json` со схемой gemini-cli).
**Если комплаенс плохой — разворот к MCP-инструментам (вариант A), где схему форсирует протокол.**

## 5. План работ (портирование на `docs/readme-and-demo-brief`)

### Этап 0 — спайк-валидация (2–3 дня, до любого кода apply-движка)
- Руками собрать пример контекста (выход `JMeterPlanSerializer.toReadableTree()` + system prompt протокола).
- 20–30 реальных задач редактирования против живых установок qwen и gigacode на Windows.
- Измерить: первичный schema-комплаенс, recovery-after-error, поддержку флагов GigaCode
  (`-p`, `--output-format json`, `--resume` — существуют ли вообще).
- Выход: go/no-go по варианту B для каждого провайдера.

### Этап 1 — порт CLI-сервисов с исправленным subprocess-слоем (~3–4 дня)
- Новый `service/cli/CliTransport` (вместо прямого ProcessBuilder в `CliAiService`):
  - Windows-резолв команды (PATHEXT / `cmd /c`), проверка JDK-8221858;
  - конкурентный дренаж stdout/stderr отдельными потоками, `waitFor(timeout)` управляет жизнью процесса;
  - промпт через stdin или временный файл (не argv); явная кодировка;
  - честная отмена: `destroy()` + `descendants()`, прокинутая в UI.
- Настоящий JSON-парсинг ответа (Jackson уже в зависимостях локальной линии — проверить версию).
- Порт `QwenCodeCliService`/`GigaCodeCliService` поверх capability record вместо наследования по префиксу.
- Регистрация провайдеров в дропдауне `AiChatPanel` локальной ветки (конфликтная зона — аккуратно).

### Этап 2 — подмешивание контекста (~3–4 дня)
- Врезать `JMeterPlanSerializer` в промпт CLI-провайдеров (режимы контекста чата уже есть на локальной линии).
- `@this` → информация об элементе уходит агенту и пишется в историю (фикс display-only).
- Фикс чередования ролей `conversationHistory` (структурированная история role+text вместо чётных/нечётных).
- `updateCurrentNode()` перед чтением; чтение дерева — снапшотом с EDT (`invokeAndWait`), не из фона.

### Этап 3 — мутации тест-плана через fenced-ops (~1–1.5 недели)
- Схема операций + парсер + валидатор (`service/ops/`), извлечение fenced-блока (последний полный).
- Маршрутизация применённых ops через существующий `plan/`-конвейер: превью (`PlanPreviewRenderer`),
  подтверждение, применение на EDT, снапшот-откат (`PlanApplyUndoStore` → кольцевой буфер).
- nodeId-реестр + revision-hash + dirty-flag конфликт-гард.
- Генерация целого теста: `new_test_plan` → JMX-фрагмент через `SaveService` → загрузка с превью.
- Отключить regex-перехват `JMeterElementRequestHandler` для CLI-провайдеров (AI-driven editing вместо него).

### Этап 4 — сессии и UX (~1 неделя)
- `--resume <sessionId>` для qwen (id из JSON-конверта), переотправка контекста только при смене hash.
- Стриминг `stream-json --include-partial-messages` → инкрементальный рендер + Stop.
- Фиксы threading/гонок: блокировка «нового чата» во время запроса, удаление индикатора «думает» на @code-пути,
  жизненный цикл при закрытии панели (cancel + kill tree).
- Промпт-инжиниринг протокола против реальных моделей (длинный хвост — закладывать итерации).

### Этап 5 (фаза 2, опционально) — встроенный MCP-сервер
- HTTP MCP в JVM JMeter (127.0.0.1, случайный порт, bearer-токен) с инструментами
  get/update/add/remove element + validate; генерируемый per-session `settings.json`.
- Требует решения по Java 17 в pom (JMeter 5.6.3 работает на 17) либо hand-rolled JSON-RPC (~700–900 LOC).
- Добавляется поверх B без выброса кода.
